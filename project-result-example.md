# Пример итогового решения

Рабочий документ команды: как выглядит готовый проект до того, как он написан.
Нужен, чтобы договориться о форме результата, а не обсуждать её по ходу.

Кейс: **Agentic AI для прогнозирования почасовой выработки ВЭС**, HackAlem 2026.

---

## 1. Задача в одном абзаце

ВЭС обязана заранее сообщать диспетчеру почасовой план выработки на сутки-двое
вперёд. Ошибка в плане оплачивается штрафом за небаланс. Нужна система, которая
сама берёт из открытых источников прогноз погоды по координатам станции,
переводит его в прогноз выработки по часам и пересчитывает результат, когда
приходит обновление погоды. Проверка — проигрыванием февраля 2026 день за днём,
причём каждый день должен видеть только ту погоду, которая была известна на тот
момент.

Станция: две турбины в Шелекском коридоре, Алматинская область.

| Турбина | Координаты |
| --- | --- |
| 1 | 43.645150, 78.535604 |
| 2 | 43.643198, 78.538828 |

---

## 2. Что сдаём

Одно приложение на существующем скелете репозитория — Express + React,
запускается одной командой, без Python и без внешних сервисов на старте.

Три режима работы одного и того же ядра:

| Режим | Команда | Назначение |
| --- | --- | --- |
| Боевой | `npm run forecast` | Прогноз на ближайшие 48 часов от текущего момента. То, что поставили бы на станцию. |
| Машина времени | `npm run backtest` | 28 запусков подряд за 31.01–27.02.2026. Ответ на требование кейса. |
| Дашборд | `npm start` → `localhost:3000` | Просмотр результатов и живой запуск агента на выбранную дату. |

репозитория**, а не только запустить его. Папку можно удалить и пересоздать
командой `npm run backtest` — результат побайтово тот же, потому что погода
берётся из закоммиченного кэша.

## 4. Запуск

```bash
nvm use
npm ci
npm run backtest        # 28 прогнозов за февраль, ~3 минуты
npm start               # дашборд на http://localhost:3000
```

Без ключа OpenAI работает всё, кроме текстового анализа агента: расчёт,
бэктест и дашборд не требуют внешних сервисов. С ключом добавляется
содержательный комментарий агента к каждому прогнозу.

```bash
OPENAI_API_KEY=sk-... OPENAI_MODEL=gpt-5 npm run forecast
```

## 5. API

| Метод | Путь | Что делает |
| --- | --- | --- |
| `GET` | `/api/health` | Уже есть в скелете |
| `GET` | `/api/forecast?date=2026-02-04` | Готовый прогноз из `artifacts/`, мгновенно |
| `POST` | `/api/forecast/run` | Живой запуск агента на указанную дату |
| `GET` | `/api/journal?date=2026-02-04` | Протокол решений агента за этот запуск |
| `GET` | `/api/metrics` | Качество на валидационном периоде |

Ответ `/api/forecast`:

  "issuedAt": "2026-02-04T03:00:00Z",
  "horizonHours": 48,
  "timezone": "UTC",
  "hours": [

## 9. Как устроена модель

### Главный принцип

Модель обучается на паре **«прогноз погоды, каким он был за сутки до» →
«фактическая выработка»**, а не на паре «фактический ветер → фактическая
выработка».

Причина практическая. В момент выпуска прогноза фактического ветра за
завтрашний день не существует — модель, обученная на нём, в эксплуатации
нечем кормить. Кроме того, прогнозный ветер отличается от фактического: шум,
сглаживание, систематический сдвиг. Обучение на прогнозах даёт модели тот же
вход, который она увидит в бою, и заодно позволяет выучить систематическую
ошибку метеосервиса в этой точке.

Подход называется MOS (Model Output Statistics) и является отраслевым
стандартом в ветропрогнозировании.

### Три ступени

**Ступень 1. Поправка прогнозного ветра.**
Open-Meteo считает на сетке около 9 км и усредняет рельеф. Турбины стоят в
ущелье, которое работает как сопло и разгоняет поток, — модель такого масштаба
этого не видит и систематически занижает ветер. Учим поправку по срезам
«сектор направления × месяц × время суток» на данных с середины 2024 года.

**Ступень 2. Кривая мощности.**
Эмпирическая кривая «ветер → мощность», построенная по 290 тысячам замеров
обеих турбин, монотонно сглаженная, с поправкой на плотность воздуха по
температуре.

**Ступень 3. Неопределённость.**
Распределение остатков модели в зависимости от уровня ветра даёт коридор
P10–P90. Коридор нужен и диспетчеру, и самому агенту — по его ширине он судит,
насколько доверять расчёту.

### Почему не градиентный бустинг

Три ступени реализуются на TypeScript без единой ML-зависимости, обучаются за
секунды, целиком объяснимы и укладываются в существующий стек репозитория.
Бустинг потребовал бы Python-сервиса рядом, то есть второго рантайма в Docker и
второго набора зависимостей, — а по критериям оценки за точность прогноза не
начисляется ни одного балла, зато за воспроизводимость начисляется 25.

Если останется время, ступень 1 усиливается до градиентного бустинга без
изменения интерфейса.

| --- | --- |

| Период | 11.03.2023 – 31.01.2026 |
| Строк | 142 360 (турбина 1) и 149 499 (турбина 2) |

| Температура | −19.3 … +44.0 °C |
| **Часовой пояс данных** | **UTC+6** |
| Принудительные остановки | ~760 и ~500 часов с хорошим ветром и нулевой мощностью |

### Часовой пояс — найденная ловушка

В файлах записано местное время станции, и какое именно — не указано.
Определили перебором сдвига по максимуму корреляции с метеоархивом:

| Сдвиг | Корреляция |
| --- | --- |
| 0 ч | 0.444 |
| −5 ч | 0.804 |
| **−6 ч** | **0.813** |
| −7 ч | 0.791 |

Часы станции идут по UTC+6 — старому алматинскому времени. Казахстан перешёл на
UTC+5 в марте 2024 года, станцию не перевели, и разрыва в данных на этой дате
нет. Без этой поправки все расчёты были бы сдвинуты на шесть часов.

### Кривая мощности

| Ветер, м/с | Мощность, доля номинала |
| --- | --- |
| 0–3 | 0.01 — ниже порога запуска |
| 5–6 | 0.16 |
| 7–8 | 0.43 |
| 9–10 | 0.73 |
| 11–12 | 0.96 — вышла на номинал |
| 14+ | 0.96 |

Кривые обеих турбин практически совпадают, турбина 2 стабильно ниже на 1–2%.
Значит, машины одной модели, и обучать можно общую модель с признаком турбины.

### Насколько прогноз отличается от факта

20 января 2026, ветер на высоте ротора, время выровнено:

| Час UTC | Факт | Прогноз за 1 сут | Прогноз за 2 сут |
| --- | --- | --- | --- |
| 05:00 | 4.90 | 1.56 | 1.03 |
| 08:00 | 5.18 | 2.78 | 2.94 |
| 17:00 | 6.40 | 4.58 | 4.31 |
| 21:00 | 8.88 | 7.25 | 6.86 |
| 23:00 | 10.39 | 8.61 | 7.97 |

Средняя ошибка 1.29 м/с на сутки вперёд и 1.47 м/с на двое. В 20 строках из 24
прогноз ниже факта — это и есть систематическое занижение, которое чинит
ступень 1.

Полтора метра в секунду выглядят мелочью, но кривая мощности в середине крутая:
в 21:00 факт 8.88 м/с дал мощность 0.67, а из прогнозных 7.25 м/с получилось бы
около 0.43. Ошибка в 1.6 м/с превращается в 24 процентных пункта по мощности.

## 11. Источник погоды

Open-Meteo, бесплатно и без регистрации. Два эндпоинта, оба проверены на наших
координатах и на феврале 2026:

| Эндпоинт | Что даёт | Глубина архива |
| --- | --- | --- |
| `previous-runs-api` | что метеомодель предсказывала за 1 и 2 суток до | с середины 2024 |
| `historical-forecast-api` | склейка ближних прогнозов | с марта 2023 |

Обучение и бэктест идут на `previous_runs` — это буквально «прогноз, доступный
на тот момент», ровно то, что требует кейс. Второй эндпоинт используем только
для калибровки часового пояса и диагностики.

Единицы: ветер приходит в км/ч, делим на 3.6. Сетка снапится в точку
43.620 / 78.479, высота 555 м.

## 12. Защита от подглядывания в будущее

Требование кейса: для каждого прогноза использовать погоду, известную на тот
момент, а не ставшую известной позже.

Соблюдаем не дисциплиной, а конструкцией. Весь доступ к погоде идёт через один
объект, которому на входе задан момент «сейчас». Запрос данных, выпущенных
позже этого момента, завершается ошибкой и останавливает расчёт.

```ts
// Запрещает утечку будущего на уровне конструкции, а не соглашения.
export function createWeatherGateway(asOf: Date) {
  return {
    async fetchForecast(issuedAt: Date, hours: number) {
      if (issuedAt > asOf) {
        throw new Error(
          `Утечка будущего: запрошен прогноз от ${issuedAt.toISOString()}, ` +
          `тогда как симулированный момент — ${asOf.toISOString()}.`
        );
      }
      return loadFromCacheOrNetwork(issuedAt, hours);
    },
  };
}
```

На это вешается тест: попытка достать прогноз из будущего должна падать.

## 13. Как меряем качество

Фактической выработки за февраль 2026 у нас нет — файлы обрываются 31 января,
организаторы придержали её для проверки. Поэтому собственную ошибку на тестовом
периоде мы измерить не можем и не делаем вид, что измерили.

Что делаем вместо этого:

- полноценный бэктест с метриками на декабре 2025 – январе 2026, где факт есть;
- за февраль выдаём 28 прогнозов по тому же протоколу, без метрик;
- в README пишем это прямым текстом.

Метрики валидации: nMAE и nRMSE от установленной мощности, отдельно по
горизонтам 24 и 48 часов, плюс сравнение с двумя базовыми уровнями — climatology
(средняя выработка по месяцу и часу) и persistence (вчерашний день как есть).
Модель обязана обыгрывать оба, иначе она бесполезна.

## 14. Соответствие критериям оценки

| Критерий | Баллы | Чем закрываем |
| --- | --- | --- |
| Соответствие задаче и работоспособность | 25 | Все четыре требования кейса реализованы; запуск одной командой без внешних зависимостей |
| Техническая реализация | 25 | Агент с инструментами и журналом решений, MOS-подход, guardrail против утечки будущего, тесты |
| README и воспроизводимость | 25 | Результаты и кэш погоды в репозитории плюс команда, пересоздающая их побайтово |
| Ценность и применимость | 15 | Коридор P10–P90 для диспетчера, боевой режим без машины времени, честный разговор о границах применимости |
| Потенциал и оригинальность | 10 | Найденная и исправленная ловушка с UTC+6, поправка на рельеф Шелекского коридора, архитектурный запрет утечки будущего |

За точность прогноза баллов не начисляется. Это не повод считать плохо, но
повод не тратить время на тюнинг в ущерб документации и работоспособности.

## 15. Что сознательно не делаем

Ансамбль нескольких метеомоделей, нейросети, подбор гиперпараметров,
моделирование аэродинамического следа между турбинами, отдельный Python-сервис.
Каждый пункт стоит часы и не добавляет ни одного балла по критериям.

## 16. Открытые вопросы

1. **Метрика организаторов.** В условии не названа. Если станет известна —
   подстраиваем функцию потерь. Пока считаем nMAE и nRMSE и показываем обе.
2. **Формат сдачи прогнозов.** Формат CSV выбран нами. Если организаторы
   пришлют шаблон — приводим к нему.
3. **Суммарная выработка станции.** Считаем по турбинам раздельно. Если нужен
   один ряд на ВЭС — суммируем, но тогда надо договориться, как обрабатывать
   часы, когда одна турбина стоит.
